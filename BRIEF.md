# Feature flags teaching demo: build brief

Purpose: a small, readable Node demo for a 20 to 30 minute talk to a student
developer group, then shared as a public repo they can run against their own
LaunchDarkly account. Every step must be visible in code. Simplicity beats
completeness. If a choice adds a framework, a build step or a second language,
make the other choice.

## Stack

- Node 20+, plain JavaScript (ESM), Express. No TypeScript, no bundler, no
  front-end framework. The browser page is one HTML file with inline script.
- SDKs: `launchdarkly-js-client-sdk` (browser), `@launchdarkly/node-server-sdk`
  and `@launchdarkly/server-sdk-ai` (server and scripts).
- Confirm every SDK call against the current docs before writing it; do not
  rely on memory for method names or signatures:
  - JS client SDK: https://launchdarkly.com/docs/sdk/client-side/javascript
  - Node server SDK: https://launchdarkly.com/docs/sdk/server-side/node-js
  - AI SDK and metrics: https://launchdarkly.com/docs/sdk/features/ai-metrics
  - Guarded rollouts: https://launchdarkly.com/docs/home/releases/guarded-rollouts
  - Regression detection: https://launchdarkly.com/docs/home/releases/regression-detection
  - AgentControl configs (formerly AI Configs): https://launchdarkly.com/docs/home/agentcontrol

## Repo layout

```
public/index.html      context form, banner, chat box (JS client SDK)
server.js              Express: serves public/, POST /api/chat (server SDK + AI SDK)
scripts/traffic.js     synthetic load: `node scripts/traffic.js latency|tokens`
.env.example           LD_SDK_KEY, LD_CLIENT_SIDE_ID, MODEL_API_KEY (optional)
README.md              setup for a student with a fresh LaunchDarkly account
LICENSE                MIT
```

Target sizes: index.html under 120 lines including markup, server.js under
120 lines, traffic.js under 120 lines. Comments explain the LaunchDarkly call,
not the JavaScript.

## LaunchDarkly objects (created by hand in the UI; README documents each)

- Flag `welcome-banner`, boolean, client-side SDK availability on.
- Flag `checkout-v2`, boolean, server-side. Used by the guarded rollout.
- Metric `checkout-latency`: numeric custom metric, unit ms, lower is better,
  analysis per context (average). Event key `checkout-latency`.
- AgentControl config `support-assistant` with two completion variations:
  `concise` (short system prompt, cap the answer at two sentences) and
  `verbose` (an absurdly long system prompt that demands exhaustive answers).
  Token usage is autogenerated from AI SDK track calls; no custom metric.
- Context kind: `user` with attributes `country` and `plan`. Keep the default
  context kind for rollouts as `user`.

## Demo flow the code must support, in order

1. Open the page. Enter a context: key, country, plan. The page initialises
   the client SDK with that context and shows whether `welcome-banner` is on.
   Toggling the flag in the UI flips the banner with no reload (change
   listener on the flag).
2. Add a targeting rule on `country`, then on `plan`, then both. Change the
   form, the page calls `identify()` with the new context, banner follows.
3. Set a percentage rollout. Type a new key, bucket changes. No other code.
4. Run `node scripts/traffic.js latency`. For each of N synthetic contexts it
   evaluates `checkout-v2` and then tracks `checkout-latency` for the same
   context, with the value drawn from a slow distribution when the new
   variation was served and a fast one otherwise. A guarded rollout on
   `checkout-v2` with automatic rollback detects the regression and rolls back.
5. Experiments are shown from screenshots of a separate demo environment.
   Nothing to build.
6. Chat box: POST /api/chat sends the message and the current context. The
   server fetches `support-assistant` for that context, calls the model if
   `MODEL_API_KEY` is set, otherwise returns an echo that shows the model name
   and system prompt LaunchDarkly served. Either way it records duration and
   tokens through the AI SDK tracker (fake but plausible token counts in echo
   mode, flagged as such in the response).
7. Run `node scripts/traffic.js tokens`. Same pattern as step 4: fetch the
   config per synthetic context, track token usage, large output counts when
   the `verbose` variation was served. A guarded rollout on the config, on the
   autogenerated token metric, rolls the `verbose` variation back.

## Guarded rollout mechanics the scripts must respect

These are the reasons a rollback fails to appear on stage. Build for them.

- Metric events only count when the same context evaluated the flag or config
  first. Evaluate, then track, same context object, every iteration.
- Evaluate for every context regardless of which arm it lands in, and track a
  value for every context. Skewed exposure triggers a sample ratio mismatch
  rollback, which is the wrong lesson.
- Minimum sample is 10 contexts per variation and the first rollout stage is
  small. Default N to 600 distinct keys, about 20 per second, configurable.
- Checks run roughly every 10 seconds and a regression needs 95 percent
  confidence that the new arm is worse. Make the gap unmissable: latency about
  120 ms versus 900 ms with modest jitter; tokens about 150 versus 2500 output.
- Call `flush()` and `close()` before the script exits. Print a one-line
  progress counter so the presenter can narrate.
- Use fresh context keys each run (prefix with a timestamp) so reruns are not
  deduplicated against earlier exposures.

## Hygiene for a public repo

- No keys in git. `.env.example` only; `.env` in `.gitignore`.
- README: create account, create project and environment, copy SDK key and
  client-side ID, create the flags, metric and config exactly as above, then
  `npm install`, `npm start`, `npm run traffic -- latency`. A student should
  get the banner working in under 15 minutes.
- README states plainly that the traffic scripts send synthetic data and that
  the repo is an unofficial teaching demo, not a supported LaunchDarkly product.
- Tell users to enter made-up values in the context form; the attributes are
  sent to LaunchDarkly. One sentence on private attributes with a docs link.

## Acceptance

- `npm start` serves the page; banner flips within two seconds of a flag change.
- `identify()` path works from the form without reload.
- `npm run traffic -- latency` against a running guarded rollout produces a
  detected regression and automatic rollback in under three minutes, twice in
  a row, in a fresh environment.
- `npm run traffic -- tokens` does the same on the config.
- Echo mode works with no model key set. A real model call works when one is set.
- Fresh clone to working banner in under 15 minutes following only the README.

## Out of scope

Experiments, migration flags, observability plugins, Docker, tests beyond a
smoke check of each script, any UI beyond what the steps above need.
